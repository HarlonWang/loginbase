> **讨论纪律（2026-08-17 定）**：分四层，**上层不定稿不进下层，下层的内容不往上层带**。
> 讨论中冒出的连带问题一律记进文末「待议清单」并标层级，不就地展开。
>
> | 层 | 只回答一件事 | 状态 |
> |---|---|---|
> | L1 目的与边界 | 给谁看、看什么类问题、什么不在范围 | ✅ 定稿 |

## L1 目的与边界（定稿 2026-08-17）

**受众**：App 产品 + 运维，两类人看同一个盘。

**要回答的两类问题**：

1. **用户情况**——多少人在登录、新老构成、用什么方式登、来自哪个国家。
2. **异常情况**——哪一步在掉人、错在哪、以此驱动改功能和修 bug；**重点是浏览器带回跳的 OAuth 链路**，它段数多、跨端、失败静默。

**载体**：数据落 Cloudflare D1。**本期不做看板**，指标定稿后先解决数据有无的问题。

**客户端配合范围（档 1+2，定稿 2026-08-17）**：客户端（`loginbase-kt` + 消费方 App）会为本需求做配合改动，两档都做——

| 档 | 做法 | 解锁 |
|---|---|---|
| 档 1 | 在**已有请求**上带客户端标识（版本、平台） | App 版本 / 平台两个切片轴 |
| 档 2 | 客户端**主动上报事件** | D15~D19、C8、F9 等标 `[客]` 的指标；②、④ 两段黑洞的拆分**全部依赖它** |

档 2 是必需的，因为「用户空手回到 App」「回跳被劫走」这类场景的共同特征就是**后面没有任何请求了**——档 1 一个字都补不了。代价（滥用面、端点形态、来源可信度）属 L3/L4，已入待议清单。

**明确不在范围内**（客户端配合后仍然答不了）：

| 问题 | 为什么答不了 |
|---|---|
| 授权页上「用户主动取消」vs「页面根本没加载出来」 | 浏览器内部对 App 不可见，iOS 的 cancel 回调也只说会话被关了、不说原因。**注**：这段黑量本身已可拆三份（见 D15~D17），不可分的只剩这一对原因 |
| deepLink 被别的 App 劫持后的**去向** | 被接走时我们的客户端什么都收不到。**注**：「回跳丢了」这个事实的判定已可得（见 D18/D19），拿不到的只是它去了哪 |
| **logto vs loginbase 双轨占比** | 不是客户端能力问题——logto 轨根本不经过本库；退役决策的数据源只能是消费方 `requireAuth` 的 track 打点。何况 Logto 即将退役 |
| 邮件的真实投递/打开结果 | 与客户端无关，需接 Resend webhook（新外部依赖） |

**由来**：`plan.md`「D 层观察期读数」那次三源手工取数暴露了两个硬伤——Workers Logs 保留 7 天、Logto 审计日志 3 天，历史基线**已永久不可得**；且取数姿势难复现（observability API + 客户端埋点分世代）。本需求即把那次一次性的考古动作，变成长期稳定、口径固定、可回溯的登录数据视图。

## L2 指标清单（定稿 2026-08-17）

### 核心指标（10 条）

下表 `核` 列打 `✓` 者即核心，定义是**「没有它这个盘就不值得上线」**。

| # | 指标 | 为什么是核心 |
|---|---|---|
| A2 | 日登录独立用户 | 「多少人在用」的基准数，一切比例的分母 |
| A3 | 日新增用户 | 增长看它；也逼出「新老用户」这个必需字段 |
| B1 | 方式占比 | 邮箱轨与 GitHub 轨的资源投入靠它分配 |
| K3 | 用户归属国分布 | 国家维度的落点，且是抗代理扭曲的那个口径 |
| C2 | 发码→验码转化 | 邮箱轨的总体健康，一个数看穿 |
| C3 | 验码失败率与分因 | 邮箱轨出问题时唯一能定位到原因的 |
| **D11** | **回跳丢失数 / 率** | 本需求点名要解决的那类问题，全盘最值钱的一个数 |
| D4 | OAuth ①→③ 流失率 | 授权页那段的总量哨兵，且不依赖客户端就能出数 |
| F2 | 救活率 | 会话机制是否正常工作；顺带逼出 F1 这个缺失的分母 |
| G1 | 发信失败数与错误码 | 邮件是邮箱登录的命脉，断了整条链就没了，而现在完全不留痕 |

**核心清单的用途**（不是「只做这些」）：

1. **L3 取舍的裁判**——为核心指标必须付的成本就付，只为备选指标才需要的成本就砍或延后。没有这份清单，每个字段都会显得「好像有用」。
2. **一期验收标准**——核心指标全部能出数即 done。
3. **分期依据**——备选里被同一批字段顺带覆盖的白送；需要额外代价的（额外客户端上报、额外的表）进二期。

**几个故意没进核心的，理由留档**：D14 端到端成功率可由 D4 + D11 推出；D15~D19 是 D4/D11 的**支撑**而非独立目标，且绑在客户端落地进度上；D12（otc 失效）很想要但属 D11 的下钻；A1、H1 重要但便宜，几乎必然被顺带覆盖，不必占名额。

### 其余条目的地位

非核心项一律为**备选**：留在清单里，多数会被顺带实现，**但口径不预先抠死**——真要看的时候再定（如 K2）。

指标名后的 **`[客]` = 依赖客户端主动上报**（档 2），意味着落地滞后于服务端且数据本质不完整（见下方口径约定 5、6）。

### 公共口径约定

| 约定 | 取法 | 理由 |
|---|---|---|
| 时区分桶 | 原始时间存 UTC，**聚合一律按 Asia/Shanghai 分天** | 上次取数 UTC 与 CST 混读，8 小时差会把一天的量摊到两天 |
| 「一次登录成功」 | = **客户端真正拿到 token 对**（邮箱验码成功 / OAuth exchange 成功）。OAuth 的 callback 建会话另记作「服务端签发成功」 | 二者之差即回跳丢失；混成一个数这个洞永远看不见 |
| 失败率的分母 | 每段用**上一段的成功数**，不用「总尝试数」 | 漏斗才自洽 |
| 「登录次数」 | 一次登录 = 一条新会话链的诞生，不含后续续期 | 会话续期会不断产生新行，直接数行数会严重虚高 |
| **客户端上报只细化分子** | 凡 `[客]` 指标，**比例可信、绝对值不可信**；分母一律取服务端侧的数 | 客户端数据的缺失是本质的而非 bug——App 被杀、离线、卸载，事件就永远丢了。不写死这条，将来必被当精确值读 |
| **`[客]` 指标必须按 App 版本分组** | 且要明确定义「未上报世代」的兜底口径（通常是单独成桶，不摊进任何比例） | 客户端独立版本线、落地滞后，长期存在不上报的老版本。上次三源取数的「成功率 150%」就是混算两代埋点得出的，同款坑 |

### D. OAuth 登录漏斗

口径基础——五段链路：① start 发起 → ② GitHub 授权页（**不经过我们**）→ ③ callback 回来 → ④ 302 回跳 deepLink → ⑤ exchange 换 token。

| 核 | # | 指标 | 口径 |
|---|---|---|---|
|  | D1 | ① 发起数 | count(start 成功) |
|  | D2 | 回跳地址不合法数 | 白名单未命中；几乎必是配置错，非零即报警 |
|  | D3 | ③ callback 到达数 | count(callback 进入) |
| ✓ | D4 | **①→③ 流失率（总量）** | 1 − D3/D1；授权页取消 + 打不开 + 链路差的合计。拆分见 D15~D17 |
|  | D5 | state 失效数 | state 过期（10 分钟）或已消耗；此时用户卡在浏览器页面上 |
|  | D6 | 换 token 失败数 | 向 GitHub 换码或取用户信息失败；GitHub 侧故障哨兵 |
|  | D7 | 拿不到邮箱数 | provider 无 verified email，用户被挡在门外 |
|  | D8 | 建号回调异常数 | 消费方 `onVerified` 抛错；消费方 bug 哨兵 |
|  | D9 | ③ 签发成功数 | callback 成功签发一次性授权码 |
|  | D10 | ⑤ 兑换成功数 | count(exchange 成功) |
| ✓ | D11 | **回跳丢失数 / 率** | D9 − D10。**本盘最值钱的一个数** |
|  | D12 | 一次性码失效数 | otc 过期（60 秒）或已消耗；即「60 秒够不够」的判据 |
|  | D13 | 回跳耗时分布 | exchange 时刻 − callback 时刻（p50/p90/max）；比 D12 更早预警 |
|  | D14 | 端到端成功率 | D10 / D1 |
|  | D15 | 送入浏览器数 `[客]` | 客户端确认已把用户送进授权页 |
|  | D16 | 空手返回数 `[客]` | 用户回到 App 但没有回跳；**「取消」与「页面打不开」合计，二者不可分** |
|  | D17 | 彻底失联数（推导） | D1 − D3 − D16；用户再没回到 App（进程被杀、放弃、切走不回） |
|  | D18 | 回跳到达数 `[客]` | 客户端确实收到了回跳 |
|  | D19 | 回跳未到达数（推导） | D9 − D18；即 D11 中「被劫走 / 浏览器没弹」的那部分，与「到达但兑换失败」（D12）区分开 |

### K. 国家与地域

数据来自 Cloudflare 请求上下文自带的地理字段，无外部依赖。

| 核 | # | 指标 | 口径 |
|---|---|---|---|
|  | K1 | 登录国家分布（事件口径） | 按国家分组的登录成功**次数** |
|  | K2 | 登录用户国家分布（当期） | 按国家分组的**独立用户数**；跨国用户重复计入还是按当期最近一次归一——**备选项，口径待用时再定** |
| ✓ | K3 | 用户归属国分布（累计） | **按首次登录时的国家给用户永久打标**（已定 2026-08-17）；回答「我的用户是哪国人」，不随漫游漂移 |
|  | K4 | 新增用户国家分布 | A3 × 国家 |
|  | K5 | 国家 × 登录方式 | B1 × 国家；两个分布的**差**本身是信号（见下面口径坑①） |
|  | K6 | 国家 × 各段成功率 | D 漏斗按国家拆 |
|  | K7 | 跨国用户数 / 占比 | 同一用户在窗口内出现 ≥2 个国家；账号共享 / 被盗 / 换代理的哨兵 |
|  | K8 | 国家未知占比 | 地理字段缺失的比例；数据质量哨兵 |
|  | K9 | 网络（ASN）分布 | 按自治域分组；能区分家宽与云厂商出口，是识别代理最实用的手段 |

**K 组的三条口径坑（读数前必看）**：

1. **代理会系统性扭曲这组数，且是偏向性扭曲**。用户主要在国内，而访问 GitHub 授权页本身就需要代理——**走 GitHub 登录的用户天然更可能挂着代理**，其国家分布会系统性偏向 US/JP/SG，邮箱轨则更接近真实。产品口径应以**邮箱轨或 K3 归属国**为准；GitHub 轨的国家数据先当「出口分布」读。同理 **K6 看的是出口质量而非地域链路质量**——仍有用（能发现某类出口特别容易丢回跳），但别按字面解读。
2. **地理字段会缺失**（本地开发、测试环境、特殊来源），必须落成 `unknown` 单独成桶，不能当成一个国家混进饼图；K8 就是盯这个的。
3. **长期分布受保留期限制**——K3 与年度趋势会被原始数据保留期截断。解法属 L3/L4，已入待议清单。

### 切片维度（每个指标都可拆的轴）

登录方式 / 国家 / 网络(ASN) / 客户端大类 / 邮件语言 / 新老用户 / **App 版本 `[客]`** / **平台（Android、iOS）`[客]`**。

后两个由档 1 解锁（已有请求带客户端标识，成本近乎为零）。**App 版本这条别当边角**——它是 `[客]` 指标能不能读的前提（见公共口径约定 6），也让服务端盘自己就能分世代，不必再像上次取数那样人工分组。

## 待议清单（L2 定稿前不讨论）

**L3 数据模型**

- 用户首登国家存哪：从事件表现算会被保留期截断，需要一张只增的用户维度小表？
- 是否给 `onVerified` 的 `requestMeta` 补 country / asn（可选字段，minor 非 breaking），让消费方建档时即可用
- 续期成功路径当前不发事件，导致 F2 没有分母
- 长期趋势（A5/A6/B4/K3）是否需要按天聚合的汇总表
- 漏斗串联需要一个贯穿 ①③⑤ 的标识；**不可用 state / otc 充当**（单次凭证不进长期表）
- 「登录方式」目前不在会话表里，从事件取
- 档 1：客户端标识走什么 header、格式如何、是否所有端点都带
- 档 2：上报端点的形态——事件名白名单、限流、要不要认证、匿名事件（登录前就发生）怎么处理
- 客户端事件与服务端事件同表还是分表；无论如何**来源必须可区分**，否则客户端的不完整数据会污染服务端的权威分母
- 客户端上报的漏斗标识如何与服务端的对齐（D15~D19 全靠它才能和 D1/D3/D9 对上）

**L4 非功能**

- ASN 存不存、存数字还是组织名（隐私增量 = IP 删除后仍存活的网络画像残留）
- 邮箱是否只存哈希、IP 保留 30 天、事件保留 90 天
- 库内建可选模块（默认关闭）vs 消费方自建
- 会话表无清理策略（既有问题，会被本需求顶到台面）
